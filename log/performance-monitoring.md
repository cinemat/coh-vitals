# Моніторинг продуктивності — childrenheroes.org

Робочий журнал для відстеження прогресу за метриками Core Web Vitals та суміжними показниками під час виконання плану виправлень (`readme.md`). Кожен новий замір додається новим рядком знизу — так одразу видно тренд.

## Методика

- **Lab-таблиці (нижче):** дані з Google PageSpeed Insights API (Lighthouse-рушій), окремо для mobile і desktop. Джерело — `www.googleapis.com/pagespeedonline/v5/runPagespeed`, ключ у `.env` (`PAGESPEED_API_KEY`).
- **Field-таблиця:** реальні дані користувачів із **CrUX** (Chrome UX Report), 28-денне ковзне вікно, персентиль p75. Ці дані оновлюються повільно (раз на кілька днів), тому їх не потрібно знімати при кожній правці коду — досить раз на 1–2 тижні.
- **INP вимірюється тільки польовими даними** — жоден лабораторний інструмент (Lighthouse/PSI lab) не може відтворити реальну взаємодію користувача, тому в lab-таблицях замість INP стоїть TBT (Total Blocking Time) як лабораторний проксі-індикатор ризику поганого INP (див. методику аудиту, розд. 2 PDF).
- **Одиничний прогін vs медіана:** з початку аудиту зафіксовано великий розкид лабораторних значень між сесіями через автослайдер і динамічний сторонній JS (розд. 1 PDF). Разові PSI-заміри тут познач. `(1 прогін)`. Для контрольних точок після значних правок рекомендовано робити 3 прогони і брати медіану (`(медіана×3)`), як у методиці аудиту.

### ⚠️ Нова знахідка (не в оригінальному аудиті): реальний CLS на `/en/` — SLOW

Лабораторний CLS на `/en/` майже ідеальний (0,006–0,049), але **реальні відвідувачі бачать зовсім інше**: ~60 % користувачів `/en/` desktop і подібна частка mobile потрапляють у категорію CLS > 0,25 (SLOW). Це означає, що лабораторний тест (холодне завантаження, немає взаємодії, немає persoналізації) **не відтворює те, що ламає верстку в реальних умовах** — ймовірні кандидати: chat-віджет/попапи/банер cookies/реклама, що з'являються з затримкою після взаємодії користувача, чого Lighthouse не встигає зафіксувати. На `/` (українська версія) цієї проблеми немає (CLS FAST в обох джерелах даних).

**Рекомендація:** додати окрему діагностичну задачу — RUM-моніторинг CLS з розбивкою по джерелу зсуву (`web-vitals` CLS attribution API) саме для `/en/`, оскільки жодна із задач 1.1–3.8 плану виправлень не націлена конкретно на цей розрив між lab і field. Ключові підозрювані: попапи (SP Popups), live chat (Pulse), TikTok/Clarity, що вантажаться асинхронно на цій локалі.

## Як оновлювати цей файл

1. Джерело даних — Google PageSpeed Insights API: `https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url={URL}&strategy={mobile|desktop}&category=performance&key={PAGESPEED_API_KEY}`, ключ читається з `.env`.
2. З відповіді API беруться: `lighthouseResult.categories.performance.score` (lab-оцінка), `lighthouseResult.audits.*` (LCP/CLS/FCP/TBT/SI/TTFB/вага/запити), `loadingExperience.metrics.*` (field-дані CrUX, якщо є).
3. Додайте новий рядок у відповідну таблицю (mobile/desktop/field) з датою і коротким коментарем, яку задачу з `readme.md` щойно виконали — так прогрес одразу прив'язується до причини.
4. Для контрольних точок після завершення етапу (0→1→2→3) рекомендовано 3 прогони й медіана — так само, як методика в оригінальному аудиті.
