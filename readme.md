# Children of Heroes — Performance Audit → ClickUp Task Breakdown

> Аналіз документа `childrenheroes-performance-audit-plan-2026-07-31.pdf` (діагностика продуктивності сайту + план виправлень) і розбивка на задачі для ClickUp.

---

## 1. Короткий висновок аудиту

Сайт у **червоній зоні мобільної продуктивності**, але **сервер — не проблема** (кешований HTML віддається за ~90–209 мс). Вузьке місце — клієнтська частина:

- **15–18 МБ** ваги сторінки, з яких **12–17 МБ — зображення**
- **~100 тегів `<script>`**, з них **53 синхронні**
- Hero-**автослайдер зриває LCP** (лабораторний LCP до 48–68 с на mobile)
- Весь маркетинговий стек (GTM, GA4, 3× Meta Pixel, TikTok, Clarity, Spotify, чат, попапи) і **платіжний чек-аут Fundraise Up (~625 КБ)** вантажаться кожному відвідувачу ще до взаємодії

Плюс два **інфраструктурні ризики**, невидимі з фронтенду:

- **Диск заповнений на 94 %** (3,9 ГБ вільно) — при вичерпанні впаде все: сайт, БД, сервіси
- **БД 3,6 ГБ**, з яких ~2,5 ГБ — сміття (30 878 ревізій постів з копіями Elementor JSON, логи redirection)
- **PHP 8.0 — EOL з 11.2023** (без security-патчів понад 2,5 роки)

### Ключові метрики: факт → ціль

| Показник | Факт | Ціль |
|---|---|---|
| Lighthouse mobile | 25–36 / 100 | ≥ 90 |
| Lighthouse desktop | 28–78 / 100 | ≥ 90 |
| LCP mobile (лаб., 4G) | 48–68 с | ≤ 2,5 с |
| TBT mobile | 880 мс – 31,6 с | ≤ 200 мс |
| Вага сторінки | 15,4–17,8 МБ | ≤ 2 МБ |
| Кількість запитів | 212–265 | ≤ 80 |
| Диск сервера | 94 % | ≤ 85 % |
| База даних | 3,6 ГБ | ~0,6 ГБ |
| Активні плагіни | 43 | обґрунтований мінімум |

**Що вже добре:** WP Super Cache + Cloudflare для статики працюють, OPcache увімкнений, CLS у нормі. Міграція хостингу не потрібна.

## 2. Як організувати це в ClickUp — рекомендація

### Структура

```
Space: Website
└── List: 🚀 Performance Optimization
    ├── Task: [Етап 0] Стабілізація і базова лінія        ← 7 subtasks
    ├── Task: [Етап 1] Критичний шлях головної сторінки    ← 8 subtasks
    ├── Task: [Етап 2] Origin, БД, кеш                     ← 4 subtasks
    ├── Task: [Етап 3] Вихід у зелену зону                 ← 8 subtasks
    └── Task: [Етап 4] Контроль якості (постійний процес)  ← 5 subtasks
```

**Чому саме так:**

1. **Етап = Task, задача аудиту = Subtask.** Етапи в плані — це логічні milestone'и з чіткою послідовністю та критерієм завершення («після Етапу 1 очікуємо mobile 55–80»). Task-контейнер дає прогрес-бар по subtasks і зрозумілу точку статусу для менеджера.
2. **«Ключові дії» кожної задачі → Checklist всередині subtask.** Не плодіть третій рівень вкладеності — checklist достатньо, і виконавець відмічає кроки.
3. **«Ефект / критерій приймання» → у Description subtask** (розділ *Acceptance Criteria*). Це готовий Definition of Done — QA/менеджер перевіряє саме по ньому.
4. **Priority ClickUp:** P0 → Urgent, P1 → High, P2 → Normal.
5. **Tags за роллю виконавця** — головний інструмент розподілу: `devops`, `wp-backend`, `frontend`, `analytics`, `qa`. Один виконавець фільтрує список по своєму тегу і бачить свій фронт робіт незалежно від етапів.
6. **Dependencies (Waiting on):** у ClickUp проставте залежності, вказані нижче в колонці «Залежить від» — це критично, бо, наприклад, чистку БД не можна починати без бекапу, а Meta-дедуплікацію — без зафіксованої аналітичної бази (0.6).
7. **Етап 4 — це не проект, а процес.** Заведіть його задачі як recurring tasks (щорелізний Lighthouse CI, щомісячний tag review) або окремий List «Performance QA», щоб він не «висів» вічно незакритим milestone'ом.

### Альтернатива (якщо команда велика)

Якщо виконавців 4+ і кожен працює у своєму списку — робіть **List = роль** (Frontend / Backend / DevOps / Analytics), Task = задача аудиту, а етап позначайте Custom Field «Phase 0–4». Але для команди 1–3 людей структура «Етап → Subtask» простіша й наочніша.

### Ролі та обсяг робіт

| Роль (tag) | Задачі | Обсяг |
|---|---|---|
| `devops` | 0.1, 0.4, 0.5, 2.2, 2.4, 4.5 | диск, бекапи, PHP, edge-кеш, алерти |
| `wp-backend` | 0.2, 0.3, 1.4, 2.1, 2.3, 3.3, 3.4 | плагіни, dequeue, БД, admin-ajax, DOM |
| `frontend` | 1.1, 1.2, 1.3, 1.8, 3.1, 3.2, 3.5, 3.7, 3.8 | hero/LCP, зображення, CSS, шрифти, JS, Fundraise Up |
| `analytics` | 0.6, 1.5, 1.6, 1.7, 3.6, 4.4 | GTM, Meta, GA4, consent, server-side tagging |
| `qa` | 0.7, 4.1, 4.2, 4.3 | Lighthouse CI, RUM, воронка пожертв |

### 📦 [Етап 0] Стабілізація і базова лінія
**Тривалість:** 0,5–1 день (задачі 0.1–0.3 ≈ 30–60 хв) · **Мета:** зняти ризик відмови сервера і зафіксувати точку відліку до будь-яких змін.

#### 0.1 · Звільнити диск ⚑ Urgent · `devops` · ~30 хв
Диск заповнений на 94 % (3,9 ГБ вільно). У `wp-content` ~730 МБ старих копій.
- [ ] Перевірити вміст каталогів `uploads___` (606 МБ), `uploads_` (90 МБ), `themes___` (23 МБ), `languages___` (13 МБ)
- [ ] Переконатися в наявності актуального офсайт-бекапу
- [ ] Видалити перелічені каталоги

**Acceptance:** +≈730 МБ; вільно ≥ 4,5 ГБ (цільове ≤ 85 % — досягається разом із 0.4 і 2.1).
**⚠️ Не робити:** не видаляти без перевірки вмісту і відновлюваного бекапу.

#### 0.2 · Деактивувати Query Monitor у продакшні ⚑ Urgent · `wp-backend` · ~10 хв
Query Monitor профілює кожен запит на проді.
**Acceptance:** плагін деактивовано, профілювання вимкнене.

#### 0.3 · Лишити один backup-плагін ⚑ Urgent · `wp-backend` · ~1 год
Зараз чотири backup-плагіни одночасно: Duplicator, Duplicator Pro, All-in-One WP Migration (+ Unlimited Extension), WPvivid, сліди UpdraftPlus.
- [ ] Обрати один інструмент з офсайт-розкладом
- [ ] **Перед видаленням решти** — тестове відновлення чинного бекапу на staging
- [ ] Видалити решту backup-плагінів

**Acceptance:** рівно один backup-механізм із перевіреним відновленням.

#### 0.4 · Аудит бекапів по серверу ⚑ High · `devops` · ~2–3 год
- [ ] Знайти й розчистити backup-артефакти поза `wp-content`
- [ ] Налаштувати ротацію та офсайт-зберігання
- [ ] Налаштувати алерт диска на 85 %

**Acceptance:** карта споживання диска; алерти активні. **Залежить від:** 0.3.

#### 0.5 · Видалити wp-file-manager ⚑ Urgent · `devops` · ~15 хв
Плагін повільний і має відомі вразливості.
**Acceptance:** плагін видалено; файловий доступ — лише SSH/SFTP.

#### 0.6 · Зафіксувати аналітичну базу ⚑ Urgent · `analytics` · ~2–3 год
Точка відкату перед будь-якими змінами тегів.
- [ ] Експортувати версію GTM-контейнера (GTM-KG5B3NH)
- [ ] Повна інвентаризація тегів/тригерів/ініціаторів: GA4, Ads, Meta ×3, TikTok, Clarity, Spotify, чат, попапи, CAPI helper
- [ ] Підтвердити наявність/відсутність Hotjar
- [ ] Зняти поточні donation conversions і checkout error rate (базова лінія)

**Acceptance:** будь-яку зміну тегів можна відкотити й порівняти з базою.

#### 0.7 · Вимірювальна база ⚑ Urgent · `qa` · ~0,5 дня
- [ ] Lighthouse у CI: 3 mobile-прогони, оцінка за медіаною
- [ ] RUM через `web-vitals` (LCP/INP/CLS → sendBeacon, код у розд. 8 PDF)
- [ ] Кастомні маркери: `hero_visible`, `donate_click`, `checkout_form_visible`, `payment_submit`, `payment_success`, `payment_error`

**Acceptance:** метрики збираються до початку Етапу 1.

### 🎯 [Етап 1] Критичний шлях головної сторінки
**Тривалість:** 2–4 дні · **Очікування після етапу:** mobile score ~55–80. **Залежить від:** Етап 0 (особливо 0.6, 0.7).

#### 1.1 · Статичний hero (зупинити автослайдер) ⚑ Urgent · `frontend` · ~0,5 дня
Автослайдер робить кожен наступний слайд новим LCP-кандидатом → LCP 48–68 с.
- [ ] Один слайд до першої взаємодії користувача; без автопрокрутки при завантаженні
- [ ] Інші слайди без реального `src` (data-src)
- [ ] Довантаження решти слайдів після взаємодії або в idle

**Acceptance:** LCP-кандидат не змінюється після першого рендера; лаб. LCP стабільний між прогонами.

#### 1.2 · Оптимізація LCP-ресурсу ⚑ Urgent · `frontend` · ~0,5 дня
- [ ] `width/height`, `fetchpriority="high"`, `loading="eager"`, `decoding="async"` на LCP-зображенні
- [ ] Умовний preload mobile/desktop через media-query (заготовка — розд. 6.1 PDF)
- [ ] Зняти `fetchpriority="high"` із зображень нижче фолда
- [ ] Один семантичний `<h1>`; заголовки неактивних слайдів — `<h2>` або поза accessibility tree

**Acceptance:** preload збігається з фактичним LCP-елементом у трейсі. **Залежить від:** 1.1.

#### 1.3 · Зображення, перший прохід ⚑ Urgent · `frontend` · ~1 день
Зображень на 12,6–17,3 МБ; 58 PNG (~7,5 МБ) не конвертовані попри встановлений Smush.
- [ ] Пережати топ-20 найважчих (список у розд. 4.1 PDF: slider-winter-camp 1,9 МБ; 600h600-1.png 1,6 МБ; solidarity 1,2 МБ …)
- [ ] Конвертувати 58 PNG → WebP/AVIF; з'ясувати, чому Smush не відпрацював
- [ ] Усунути дубль `valentines-day/1.png` (вантажиться двічі: `?v=2.2` і `?v=4.2`)
- [ ] `srcset/sizes` і реальні мобільні розміри (слот 100×67 → ~200×134 для DPR 2)
- [ ] `width/height` для всіх unsized `<img>`

**Acceptance:** сторінка 15–18 МБ → ~4–5 МБ (проміжна ціль).

#### 1.4 · Asset allowlist у WordPress (dequeue + defer) ⚑ Urgent · `wp-backend` · ~1 день
98–105 `<script>`-тегів, 53 синхронні; unused JS 610 КБ–1,2 МБ.
- [ ] Інвентаризація всіх `wp_enqueue_*`
- [ ] Умовний dequeue на головній: CF7, WooCommerce (cart/blocks/order-attribution/sourcebuster), filter-for-elementor, cabinet autologin, WayForPay, неактивні сезонні gamification-бандли
- [ ] Fancybox/Lottie — замінити нативним CSS/мінімальним кодом, якщо можливо
- [ ] Лишити **один** слайдер (Slick або Swiper)
- [ ] Прибрати jQuery Migrate після перевірки сумісності
- [ ] `defer` через нативний Script strategy API WordPress ≥ 6.3 (не regex над HTML; приклад коду — розд. 6.2 PDF)
- [ ] Регрес-тести після кожного dequeue: навігація, donate-кнопки, слайдер, перемикач мов, попапи, checkout flow

**Acceptance:** синхронних зовнішніх скриптів ≈ 0 у критичному шляху; регрес-тести пройдені.

#### 1.5 · Відкласти маркетинговий стек ⚑ Urgent · `analytics` · ~1 день
- [ ] У `<head>` — лише мінімальний GTM bootstrap (або first-party loader)
- [ ] Meta, TikTok, Clarity, Spotify, live chat, попапи — після consent / першої взаємодії / `requestIdleCallback` з таймаутом 5–8 с
- [ ] Clarity/session replay — sampling 5–10 % трафіку
- [ ] Google Consent Mode v2 (analytics_storage / ad_storage / ad_user_data / ad_personalization)
- [ ] Збір `gclid`/`fbclid`/UTM — маленьким first-party кодом одразу, без важких vendor-бібліотек

**Acceptance:** third-party main-thread до взаємодії ≤ 200 мс; атрибуція не втрачається. **Залежить від:** 0.6.

#### 1.6 · Дедуплікація Meta Pixel ⚑ Urgent · `analytics` · ~0,5 дня
Три Pixel ID з повторними PageView; `capiParamBuilder` завантажений двічі.
- [ ] Один browser PageView на кожен Pixel ID
- [ ] Один базовий `fbevents.js`-loader (не окремий на кожен pixel)
- [ ] Один `capiParamBuilder` — знайти два ініціатори, лишити один
- [ ] Client/server дедуплікація через стабільний `event_id`
- [ ] Перевірити, що ініціатор не задвоєний між кодом теми і GTM

**Acceptance:** GTM Preview + Meta Pixel Helper + Events Manager — по одній події; конверсії не подвоюються. **Залежить від:** 0.6.

#### 1.7 · GA4 / Google Ads ⚑ Urgent · `analytics` · ~0,5 дня
- [ ] Один GA4 PageView (зараз GTM + GA4 + окремий gtag/js)
- [ ] Ads-конверсія — лише після реально успішної пожертви
- [ ] Fundraise Up callback не шле ту саму конверсію окремо через тему і GTM
- [ ] Cross-domain linker для `donorsupport.co`; `gclid` не втрачається при переході на hosted checkout
- [ ] Enhanced-conversion бібліотеки — лише за потреби

**Acceptance:** DebugView/Realtime — одна подія; наскрізна атрибуція на checkout-домені працює. **Залежить від:** 0.6.

#### 1.8 · Fundraise Up за наміром ⚑ Urgent · `frontend` · ~1 день
Checkout-бандли ~625 КБ (з них ~550 КБ unused) вантажаться кожному відвідувачу до кліку на Donate.
- [ ] Легка shell-кнопка Donate
- [ ] `preconnect` до платіжних origin лише де CTA реально видимий (розд. 6.3 PDF; сумарно ≤ 4 глобальні preconnect)
- [ ] Ініціалізація чек-ауту на `pointerenter`/`touchstart`/`focus` CTA або в idle після фіксації LCP
- [ ] Повний checkout — тільки при намірі/кліку
- [ ] Звичайний `<a>` на hosted checkout — постійний миттєвий fallback
- [ ] Chat/попапи/Clarity не мають блокувати відкриття форми

**Acceptance:** `donate_click → form_visible` ≤ 300 мс warm / ≤ 800 мс cold; payment error rate і conversion tracking без регресій. **Залежить від:** 0.7 (маркери воронки).

### 🟢 [Етап 3] Вихід у зелену зону
**Тривалість:** 1–2 тижні · **Залежить від:** Етапи 1–2.

#### 3.1 · Critical CSS ⚑ High · `frontend` · ~1–2 дні
~40–42 render-blocking ресурсів (економія ~640–1220 мс); unused CSS 116 КБ.
- [ ] Інлайн критичного CSS для header + hero + першого CTA; решта — асинхронно
- [ ] Посторінковий enqueue стилів за template/наявністю блоку
- [ ] Видалити стилі неактивних сезонних плагінів; мініфікація
- [ ] ⚠️ «Combine all CSS» — не рішення: спершу не відправляти зайве

#### 3.2 · Шрифти ⚑ High · `frontend` · ~0,5 дня

Реліз/проєкт вважається успішним, якщо (медіана 3 прогонів):

| Показник | Ціль |
|---|---|
| Lighthouse mobile/desktop | ≥ 90 |
| Mobile LCP (лаб.) | ≤ 2,5 с |
| Mobile TBT | ≤ 200 мс (max 300) |
| CLS | ≤ 0,1 |
| Initial transfer | ≤ 2,0 МБ |
| Initial JS | ≤ 250–350 КБ compressed |
| Initial requests | ≤ 80 |
| Third-party main-thread до взаємодії | ≤ 200 мс |
| Donate click → форма видима | ≤ 300 мс warm / ≤ 800 мс cold |
| RUM p75 LCP / INP / CLS | ≤ 2,5 с / ≤ 200 мс / ≤ 0,1 |

## 5. Чого НЕ робити (додати в опис List як загальне правило)

- Не «малювати 90» minify/combine-плагіном
- Не preload усі hero-слайди, шрифти й платіжні скрипти
- Не ставити lazy loading на LCP-зображення
- Не переносити весь JS у footer без перевірки залежностей
- Не відкладати збір `gclid`/`fbclid`, якщо це ламає атрибуцію
- Не видаляти платіжний fallback заради балу
- Не кешувати персоналізовані/cart/checkout сторінки як публічний HTML
- Не оцінювати результат одним запуском Lighthouse — тільки медіана 3 прогонів
- Не видаляти `uploads___`/`uploads_` без перевірки вмісту й бекапу
- Не запускати масову чистку ревізій без повного дампа БД
